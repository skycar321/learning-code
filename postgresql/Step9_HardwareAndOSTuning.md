# PostgreSQL Step 9: 하드웨어 및 OS 레벨 최적화 (개념 이해 및 인프라 협업)
# (직접 제어 불가) 디스크 I/O, CPU, 메모리, 네트워크 등 하드웨어 리소스 및 OS 최적화의 중요성 이해

# 나쁜 예시: 하드웨어 사양을 고려하지 않고 데이터베이스 설정을 하거나, OS 레벨의 튜닝 없이 PostgreSQL의 성능 문제 해결을 시도합니다.
# 좋은 예시: 서버 하드웨어 (CPU, RAM, 디스크)의 특성을 이해하고 OS 설정을 최적화하여 PostgreSQL이 최고의 성능을 발휘할 수 있는 기반을 마련. 이러한 작업은 일반적으로 인프라팀과 협업합니다.

# 학습 포인트: 데이터베이스는 하드웨어와 OS 위에서 실행됩니다. 하드웨어와 OS 레벨의 최적화는 PostgreSQL 성능의 한계를 결정하는 중요한 요소입니다. 직접 접근이 어렵더라도 이러한 개념을 이해하고 인프라팀과 효과적으로 소통하는 것이 중요합니다.

---

## **중요**: 이 세션에서 다루는 내용은 대부분 데이터베이스 서버의 물리적 하드웨어 또는 운영체제(OS) 단에서 이루어지는 최적화 작업입니다. 인프라 제약으로 인해 **직접 이러한 설정을 변경하기는 어려울 수 있으므로, 항상 인프라 또는 시스템 관리팀과 협업하여 진행해야 합니다.** 이 학습은 여러분이 이러한 최적화의 중요성을 이해하고, 문제 발생 시 적절한 요구사항을 제시하거나 진단에 도움을 주기 위함입니다.

---

## 1. 하드웨어 최적화 (인프라팀 관점)

### 1.1. 디스크 I/O (가장 흔한 병목)
- **SSD 사용**: HDD보다 압도적으로 빠른 랜덤 I/O 성능을 제공합니다. 데이터베이스 워크로드에는 필수적입니다.
- **RAID 구성**:
    - **RAID 10 (1+0)**: 성능과 안정성을 모두 고려할 때 가장 권장됩니다.
    - **RAID 0**: 최고 성능이지만 데이터 안정성이 없습니다. (개발/테스트용)
    - **RAID 5**: 쓰기 성능 이슈가 있을 수 있습니다 (Write Penalty).
- **디스크 분리**:
    - WAL (Write-Ahead Log) 디렉터리 (`pg_wal`)를 데이터 파일 디렉터리와 다른 물리적 디스크에 두면 동시 쓰기 성능을 향상시킬 수 있습니다.
    - 테이블스페이스를 사용하여 특정 테이블/인덱스를 별도의 디스크에 둘 수 있습니다.
- **`noatime` 마운트 옵션**: 리눅스에서 파일 접근 시마다 접근 시간을 갱신하지 않도록 파일 시스템 마운트 옵션에 `noatime`을 추가하여 불필요한 쓰기 I/O를 줄일 수 있습니다.

### 1.2. 메모리 (RAM)
- **충분한 RAM**: `shared_buffers`, OS 파일 시스템 캐시, `work_mem` 등에 충분한 메모리를 할당할 수 있도록 충분한 RAM을 확보합니다.
- **SWAP 비활성화 또는 최소화**: 데이터베이스 서버에서는 스왑(Swap)이 발생하는 것을 피해야 합니다. 스왑은 디스크 I/O를 유발하여 성능을 급격히 저하시킵니다. OS 레벨에서 스왑 사용을 최소화하거나 비활성화해야 합니다.

### 1.3. CPU
- **코어 수**: 동시 접속자 수, 쿼리의 병렬 처리 가능성 등을 고려하여 적절한 코어 수의 CPU를 선택합니다.
- **클럭 속도**: 단일 스레드 성능이 중요한 특정 유형의 쿼리(예: 복잡한 계산)에서는 높은 클럭 속도가 유리할 수 있습니다.

### 1.4. 네트워크
- **고속 네트워크 인터페이스**: 클라이언트-서버 간 데이터 전송량이 많거나 복제(Replication) 지연이 많을 경우 기가비트 이더넷 또는 10기가비트 이더넷 NIC을 사용합니다.
- **네트워크 설정 튜닝**: OS의 네트워크 버퍼 크기 등을 조정하여 대용량 트래픽 사용을 최적화합니다.

## 2. OS 레벨 최적화 (Linux 기준 - 인프라팀 관점)

### 2.1. 커널 파라미터 튜닝
- **파일 디스크립터 제한 증가**: PostgreSQL은 많은 파일 디스크립터를 사용할 수 있으므로, 제한을 여유있게 합니다.
- **공유 메모리 설정**: `shared_buffers` 설정에 맞춰 OS의 공유 메모리 파라미터를 충분히 크게 설정해야 합니다.
- **세마포어 설정**: OS의 세마포어 파라미터를 조정합니다.

### 2.2. 오픈 파일 수 제한
- 각 프로세스가 열 수 있는 최대 파일 디스크립터 수를 충분히 크게 설정해야 합니다. (예: `ulimit -n 65536` 이상)

### 2.3. 전원 관리 설정
- 서버의 CPU 전원 관리 기능을 '고성능(High Performance)' 모드로 설정하여 CPU가 항상 최고 클럭으로 작동하도록 합니다. (절전 모드 비활성화)

### 2.4. 스케줄러 (Scheduler)
- 디스크 I/O 스케줄러를 워크로드에 맞춰 설정합니다. (예: SSD는 `noop` 권장)

### 2.5. 파일 시스템
- **`ext4` 또는 `xfs`**: 리눅스에서 PostgreSQL에 권장되는 파일 시스템입니다. `xfs`가 대규모 파일 시스템에서 더 나은 성능을 보일 수 있습니다.

## 3. PostgreSQL과 OS 간의 상호작용 이해

- **OS 파일 시스템 캐시**: `shared_buffers`는 PostgreSQL 자체 캐시이고, OS는 별도의 파일 시스템 캐시를 관리합니다. 둘이 시너지를 내거나 때로는 경합할 수 있습니다.
- **메모리 부족 문제**: `shared_buffers`와 `work_mem`의 합이 전체 RAM을 초과하지 않도록 주의해야 합니다. 그렇지 않으면 OS 스와핑을 유발하여 성능이 급락할 수 있습니다.
