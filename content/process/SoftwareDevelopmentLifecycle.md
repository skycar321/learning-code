# 개발자를 위한 프로젝트 착수 및 개발 프로세스 가이드 (A-Z)

이 문서는 비개발자(사업부서, 클라이언트)로부터 서비스 개발 요청을 받았을 때, **개발자가 반드시 확인해야 할 체크리스트**와 **아이디어부터 상품화(배포), 유지보수까지의 전체 프로세스**를 상세히 기술합니다.

---

## 1. 착수 단계: 사업부서와 소통하기 (Requirement Gathering)

비개발자는 "이런 기능이 있으면 좋겠어요"라고 추상적으로 말합니다. 개발자는 이를 구체적인 **기술 요구사항**으로 변환하기 위해 다음 질문들을 집요하게 물어보고 확정 받아야 합니다. (나중에 "이거 왜 안 돼요?" 소리 안 들으려면 필수입니다.)

### ✅ 필수 체크리스트 (The "Must-Ask" List)

#### 1.1. 목적과 범위 (Why & What) - MVP 정의
- [ ] **서비스의 핵심 가치 (Value Proposition)**: 이 서비스를 통해 사용자가 얻는 이득은 무엇인가요? (예: 집을 빨리 구한다 vs 싸게 구한다)
- [ ] **타겟 사용자 (Target Audience)**: 20대 대학생인가요, 50대 자산가인가요? (UI/UX, 모바일/웹 결정에 핵심)
- [ ] **핵심 기능 (MVP Scope)**: "이거 없으면 서비스 오픈 못한다" 하는 기능 3가지만 꼽아주세요. (나머지는 2차 오픈으로 미룹니다)
- [ ] **제외 대상 (Out of Scope)**: 이번 1차 오픈 때 "절대 안 해도 되는 것"은 무엇인가요? (범위를 명확히 자르는 것이 개발 성공의 지름길)

#### 1.2. 데이터와 정책 (Data & Policy)
- [ ] **데이터 소스**: 보여줄 데이터는 어디서 오나요? (우리가 직접 입력? 공공데이터 API? 사용자가 생성?)
- [ ] **회원 정책**: 회원가입은 필수인가요? 소셜 로그인(카카오, 네이버)은 무엇을 붙일까요? 비회원도 볼 수 있나요?
- [ ] **결제 정책**: 유료 서비스인가요? 결제 수단(카드, 간편결제)은 무엇이고, 환불 규정은 어떻게 되나요?
- [ ] **알림 정책**: 문자(SMS), 알림톡(카카오), 앱 푸시 중 어떤 것을 언제 보내나요? (비용 발생 요소)

#### 1.3. 일정과 리소스 (When & Who)
- [ ] **오픈 목표일 (Deadline)**: 언제 런칭해야 하나요? 그 날짜가 불변인가요(법적 이슈, 마케팅 예정 등)?
- [ ] **가용 예산 (Budget)**: 서버 비용, 외부 API 사용료(지도, 문자, 채팅 솔루션 등) 예산은 얼마인가요?
- [ ] **담당자 (R&R)**: 기획(화면설계), 디자인, 정책 결정은 누가 하나요? 개발자가 기획까지 해야 하나요?

---

## 2. 개발 라이프사이클 (The Development Lifecycle)

요구사항이 정리되었다면, 다음 단계로 개발을 진행합니다. 각 단계별 산출물과 주의사항입니다.

### Phase 1: 기획 및 설계 (Planning & Design)

1.  **PRD (Product Requirement Document, 제품 요구사항 정의서)**
    *   **내용**: 사업부서의 요구사항을 기능 단위로 쪼개서 정리한 문서. (User Story 포함)
    *   **개발자 역할**: "이 기능은 기술적으로 불가능해요" 또는 "이걸 구현하려면 2주 더 걸려요"라고 피드백하여 스펙을 조율합니다.
2.  **TRD (Technical Requirement Document, 기술 요구사항 정의서)**
    *   **내용**: PRD를 구현하기 위한 기술적 설계도. (시스템 아키텍처, DB 스키마, API 명세서)
    *   **보안 설계**: 개인정보(비밀번호, 전화번호) 암호화 정책, 통신 구간 암호화(HTTPS) 계획 수립.
    *   **기술 스택**: Spring Boot vs Node.js, AWS vs On-Premise 등 결정.
3.  **UI/UX 디자인**: Figma 등을 통해 화면 디자인 및 인터랙션 확정.

### Phase 2: 개발 (Implementation)

1.  **TDD (Test Driven Development) 및 테스트 코드 작성**
    *   **원칙**: 실제 코드를 짜기 전에 "테스트 코드"를 먼저 짭니다. (실무에서는 최소한 핵심 비즈니스 로직 테스트는 필수)
    *   **이유**: 개발 후반부에 코드를 수정할 때, 기존 기능이 망가지는지(Regression) 바로 알 수 있어 디버깅 시간을 획기적으로 줄여줍니다.
2.  **Backend & Frontend 개발**
    *   **API 개발**: 프론트엔드가 화면을 그릴 수 있게 데이터(JSON)를 주고받는 서버 로직 구현.
    *   **화면 개발**: 사용자가 조작할 웹/앱 인터페이스 구현.

### Phase 3: 검증 (Verification & QA)

1.  **단위 테스트 (Unit Test)**: 개발자가 자기 코드가 의도대로 동작하는지 함수 단위로 체크.
2.  **통합 테스트 (Integration Test)**: 로그인 -> 상품검색 -> 장바구니 -> 결제까지 전체 흐름이 이어지는지 체크.
3.  **QA (Quality Assurance)**: 전문 테스터나 기획자가 "사용자 입장"에서 앱을 쥐잡듯이 사용하여 버그를 찾음.

### Phase 4: 배포 및 운영 (Deployment & Ops)

1.  **Staging 배포**: 실제 운영 환경과 똑같은 가짜 환경(Staging)에서 마지막 리허설 진행.
2.  **Production 배포**: 실제 사용자에게 서비스 오픈. (Blue/Green 배포 등 무중단 배포 전략 고려)
3.  **모니터링**: 서버가 죽지 않았는지, 에러는 없는지 실시간 감시 (Sentry, Datadog, CloudWatch 등).

### Phase 5: 유지보수 (Maintenance)

1.  **VOC 대응**: "로그인이 안 돼요", "화면이 깨져요" 같은 사용자 문의 처리.
2.  **업데이트**: OS 버전 업데이트 대응, 보안 패치, 2차 기능 개발.

## 3. [시나리오 예시] "부동산 직거래 앱" 개발 요청

### 상황:
사업부 김부장님이 찾아왔습니다. *"요즘 중개수수료 너무 비싸잖아. 대학생들끼리 자취방 직거래하는 앱 하나 빨리 만들어보자."*

### 1. 착수 단계 (인터뷰 - 개발자의 날카로운 질문)

**개발자(나)**: "부장님, 좋은 아이디어네요. 몇 가지 확인이 필요합니다."

*   **Q (타겟/인증)**: "대학생만 쓰나요? 그럼 **학교 이메일 인증(.edu)**을 필수로 넣을까요? 아니면 누구나 가입 되나요?"
    *   *A (사업부)*: "아, 학교 인증 넣읍시다. 신뢰도가 중요하니까. 외부인은 못 들어오게."
    *   -> **[기술검토]** 대학교 이메일 인증 API 필요 (비용 발생 가능), 인증 메일 발송 SMTP 서버 구축 필요.
*   **Q (데이터)**: "처음에 매물이 없으면 앱이 텅 비어 보일 텐데, **초기 매물 데이터**는 어떻게 확보하나요?"
    *   *A (사업부)*: "일단 에브리타임 같은 커뮤니티 글을 긁어와서(크롤링) 보여주면 안 될까?"
    *   -> **[법적/기술검토]** 타 사이트 크롤링은 저작권법 위반 소지가 큼. 법무팀 확인 필수. 기술적으로도 사이트 구조 바뀌면 계속 수정해야 함. -> **직접 등록 이벤트**로 유도 제안.
*   **Q (핵심기능)**: "채팅 기능이 필요한가요? 아니면 그냥 집주인 전화번호만 공개하나요?"
    *   *A (사업부)*: "요즘 애들 전화 공포증(Call Phobia) 있어서 전화 싫어해. **앱 내 채팅** 무조건 있어야지."
    *   -> **[예산/기술검토]** 채팅 서버 직접 개발(WebSocket)은 난이도가 높고 유지보수가 헬임. **Sendbird 같은 유료 솔루션** 쓸 예산이 있는지 확인. 없다면 "쪽지 보내기" 정도로 스펙 다운 제안.

### 2. 기획 및 설계 (PRD -> TRD)

*   **PRD (기능 확정)**:
    *   기능 1: 학교 이메일 인증 회원가입 (재학생 인증).
    *   기능 2: 내 방 사진 찍어 올리기 (위치 정보 포함).
    *   기능 3: 1:1 실시간 채팅 (외부 솔루션 사용).
*   **TRD (기술 설계)**:
    *   **서버**: Spring Boot (Java, 안정성 중요).
    *   **DB**: MySQL (회원, 매물 정보), MongoDB (채팅 내역 저장 - 대용량 텍스트).
    *   **지도**: 네이버 지도 API (한국 주소 검색 최적화).
    *   **보안**: 비밀번호 BCrypt 암호화, 매물 상세 주소(동/호수)는 계약 전까지 블라인드 처리.

### 3. 개발 (Development)

*   **Backend**:
    *   `User` 테이블 설계 및 이메일 인증 로직 구현.
    *   `Room` 테이블 설계 (위도/경도 저장, 사진 업로드 S3 연동).
    *   채팅 솔루션(Sendbird) API 연동 테스트.
*   **Frontend (App)**:
    *   Flutter로 개발 (iOS, Android 동시 출시 비용 절감).
    *   카메라 권한 획득 및 사진 업로드 UI 구현.
    *   네이버 지도 SDK 붙여서 매물 마커 표시.

### 4. 검증 및 배포

*   **QA 이슈 발견**: "학교 인증 메일이 스팸함으로 빠져서 가입이 안 돼요!"
    *   -> AWS SES(이메일 서비스)의 신뢰도 설정(DKIM/SPF) 추가하여 해결.
*   **배포**: 구글 플레이스토어, 애플 앱스토어 심사 제출.
    *   **[주의]** 애플은 "사용자 신고 기능(악성 매물 신고)"이 없으면 심사 거절함. 급하게 신고 기능 추가.

### 요약: 개발자가 신경 써야 할 "한 끗"

1.  **기획 단계**: "안 되는 건 안 된다"고 빠르게 말해주기. (무리한 일정/스펙은 프로젝트 폭파의 지름길)
2.  **개발 단계**: "나중에 데이터 100만 개 되면 어떡하지?" 미리 고민하기. (DB 인덱스, 쿼리 최적화)
3.  **운영 단계**: "에러 나면 나한테 문자/슬랙 오게 해두기." (사용자가 항의하기 전에 먼저 알기 위해)
